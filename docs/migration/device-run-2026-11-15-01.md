# First non-persistent hardware boot

Date: 2026-11-15

## Candidate binding

```text
boot.img SHA-256:
935a54dfe1afa622e4bfad6cdd9ed4cd8a04190fa9021d7f2cae7e3e1eb36c06
```

The host ran:

```sh
adb reboot bootloader
fastboot product msm8998
fastboot boot <candidate boot.img>
```

Fastboot reported `Sending OKAY` and `Booting OKAY`. After more than 30 seconds,
the host had no ADB or Fastboot device. The user selected `OnePlus 5 IOS`
manually. DarwinBoot ran briefly and returned to the same UniXNU menu.

No reboot, flash, dd, erase, format, GPT or slot operation was performed after
the candidate boot.

## Confirmed failure path

The ADT requests a `0x100000000` byte DarwinBoot memory window and does not have
`darwinboot-memory-excluded`. In the pinned DarwinBoot implementation, that
selects the contiguous `AllocateWindow` path rather than the multi-run
`AllocateSpan` path.

The visible string is emitted by DarwinBoot
`DarwinBootPkg/Driver/DarwinBoot.c`, `AllocateWindow`:

```text
NO WINDOW %lx BIG RUN %lx @ %lx
```

The candidate uses DarwinBoot `2ba9cad556f1794fb74ac8af164bc34b0e096338`,
which is based on upstream `5243c68e` and retains this allocation path. The
photo values decode as:

```text
requested window 0x100000000 bytes (4 GiB)
largest free run 0xfccd0000 bytes (3.950012 GiB)
run start        0x01800000
run end          0xfe4d0000 (exclusive)
shortfall        0x03330000 bytes (51.188 MiB)
```

Source return chain in the pinned lineage:

```text
DarwinBoot/DarwinBootPkg/Driver/DarwinBoot.c:581  AllocateWindow diagnostic
DarwinBoot/DarwinBootPkg/Driver/DarwinBoot.c:961  contiguous allocation call
DarwinBoot/DarwinBootPkg/Driver/DarwinBoot.c:1223 Fail prints boot refused
UniXNU/package/UniXNUPkg/Library/UniXNULib/Boot.c:58   LocateProtocol
UniXNU/package/UniXNUPkg/Library/UniXNULib/Boot.c:165  RunXnu
UniXNU/package/UniXNUPkg/Library/UniXNULib/Main.c:166  returned-status notice
```

No conventional-memory run is large enough for a single 4 GiB allocation.
`AllocateWindow` returns `EFI_OUT_OF_RESOURCES`; DarwinBoot's `Fail` path returns
that status to the UniXNU loader protocol. `UniXNUBootEntry` propagates it and
`Main.c` redraws the menu with countdown disabled. The menu therefore displays
`Select an entry`, while the direct-framebuffer `NO WINDOW` diagnostic remains
visible above it.

The status is not silently swallowed. The menu should also contain a smaller
`'OnePlus 5 IOS' returned: Out of Resources` notice, but the supplied photo
description does not include it. The `NO WINDOW` draw occurs only after the
allocation search fails, which is sufficient to identify this path.

This is not an XNU panic and not harmless boot-time telemetry. It is a failed
DarwinBoot allocation. The UEFI menu itself is healthy and the EFI application
remains resident after the loader returns.

The boot image load metadata does not overlap:

```text
kernel   0x10000000 + 0x181b63
ramdisk  0x12000000 + 0x04c00000
tags     0x18000000
```

Those ranges do not explain the missing 51.188 MiB in the 4 GiB request by
themselves. The decisive observation is the actual UEFI longest-run report.

The older H380-H403 format 1 runs all used non-persistent `fastboot boot` and
reached XNU and IOKit. H403 retained logs through about 687 seconds, including
`NATIVE_UFS_ALIVE`, GIC/timer samples and container-path activity. Those runs
rule out a generic inability of this phone/ABL path to pass BootShim, UEFI and
DarwinBoot. Their UEFI screens were not captured, so they do not explain this
candidate's particular memory map.

## Menu text

The observed menu has:

```text
OnePlus 5 IOS                 [selected]
Restart action
Select an entry
```

The `action` suffix is the UI's entry-type label. It is not a second executable
action and does not change the selected XNU entry.

## Minimal next host changes

The preferred first change is configuration-only:

1. In `board.toml`, lower `[payload.adt].owned_memory_size` from
   `0x100000000` to a 2 MiB-aligned value below the measured run.
   `0xf0000000` (3.75 GiB) leaves a conservative margin for alignment and
   future firmware-map variation.
2. Rebuild the ADT, payload, FD and boot image with the existing pinned inputs.
3. Verify the generated ADT reports the new size and rerun all 47 checks,
   FD/FV, boot-image and manifest checks.
4. Record the new boot image SHA-256 before another non-persistent
   `fastboot boot`.

Do not use the excluded-range path yet. The current iPadOS 17.7.11 profile does
not carry `window-memory-excluded-ranges.patch`, so a
`darwinboot-memory-excluded` property would advertise functionality the kernel
has not been proven to consume.

If an explicit status hold is still wanted before changing memory size, the
smallest diagnostic patch belongs in the DarwinBoot submodule:

- after the allocation error in `DarwinBoot.c`, draw
  `NO KERNEL WINDOW %r size=0x...` through `DiagDraw`;
- stall for 15 seconds before the normal `Fail` return.

That patch is not required to establish this failure: the photo plus the
`AllocateWindow` source path already identify it.

## Device state

No host command was issued after the phone returned to the menu. The current
request is evidence collection only while the device remains usable.

## Recovery plan

This was prepared but not executed.

1. Hold Power for about 10-15 seconds until the phone powers off.
2. From powered off, hold Volume Down + Power.
3. Release Power after the OnePlus logo appears while continuing to hold
   Volume Down until the installed recovery starts.
4. If Android starts normally instead, return here before issuing any host
   command; a later confirmed `adb reboot recovery` is the non-destructive
   fallback.

Do not use `fastboot flash` to recover. The current boot/recovery raw backups
remain available outside the repository if a separately confirmed restore is
ever required.
