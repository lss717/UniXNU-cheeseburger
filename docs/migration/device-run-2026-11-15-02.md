## Window selection

Historical H236br-H236bu measurements on this firmware rejected a single
256 MiB `AllocatePages` request in every tested address/type mode, while a
128 MiB request succeeded. The second candidate therefore uses:

```text

```

77,725,500 bytes before alignment and the early VM reserve.

## Exception address semantics

The text originates in `ArmPkg/Library/DefaultExceptionHandlerLib/AArch64/DefaultExceptionHandler.c`.
Line 208 prints:

```c
SystemContext.SystemContextAArch64->ELR
```

Therefore `0x000000017ADBC378` is the **exception instruction address (PC)**,
not FAR and not LR. The context also contains `ESR`, `FAR`, `SPSR`, `LR`, and
`SP`, but the current RELEASE build compiles the detailed dump under `DEBUG`
and displays only the first ELR line.

The current `DarwinBoot.efi` has:

```text
ImageBase             0x0
SizeOfImage           0xC000
SectionAlignment      0x1000
.text                 0x1000..0xA000
```

The runtime `LoadedImage.ImageBase` is not present in the photo, serial log or
saved candidate JSON. Because the PE is relocatable, the exception address
cannot be mapped to a DarwinBoot symbol without that base. An aligned-base
search produces several of these possible offsets:

| Runtime base hypothesis | Offset | Symbol at that offset |
| --- | ---: | --- |
| `0x17ADB9000` | `0x3378` | `Boot`, near `Boot.c:887` |
| `0x17ADB8000` | `0x4378` | `RamdiskLayout` |
| `0x17ADB7000` | `0x5378` | `ReadBootVideo` |
| `0x17ADB6000` | `0x6378` | `GetMap` |

These are hypotheses, not attribution. The exact function remains unresolved
until the exception screen reports `ImageBase` and image name.

## Post-dispatch path

`RunXnu` logs the line at `Boot.c:92` and calls `Loader->Boot` at line 93.
Within DarwinBoot `Boot`, the path before its first normal `DARWINBOOT:` detail
line is:

1. validate request and exception level;
2. `RamdiskLayout`;
3. copy and validate boot arguments;
4. open the payload volume;
5. `ReadFile(kernel)` and `ParseKernel`;
6. `ReadFile(ADT)` and `AdtNode`;
7. read trust cache, GPU addon and root policy sidecars;
8. `ReadBootVideo`;
9. `AllocateWindow`;
10. `PlaceImage`, `ZeroMem`, and copy kernel/ramdisk/sidecars;
11. print `DARWINBOOT: ARM64 ...`.

An exception before the `DARWINBOOT: ARM64 ...` line can therefore be in any of
those stages. The previous 4 GiB failure reached `AllocateWindow`; the same
request now reaches a different exception but the current evidence does not
identify the new stage.

`0 staged kext(s)` is expected: `unixnu.toml` sets `[kits] autoload = false`
and has no `[[entry.kext]]` entries. `UniXNUStageKexts` returns success with
count zero. This line is not the root cause.

## Minimal diagnostic fix

No memory, UFS, USB or kernel layout change is justified yet. The next image
should only improve exception evidence:

1. In
   `edk2-msm8998/Common/edk2/ArmPkg/Library/DefaultExceptionHandlerLib/AArch64/DefaultExceptionHandler.c`,
   print an unconditional one-line record containing:
   `ELR`, `SPSR`, `ESR`, `FAR`, `LR`, `SP`, `FP`.
2. In the same handler, call the existing `GetImageName(ELR, &ImageBase, ...)`
   even in RELEASE mode and print `image name`, `ImageBase`, and
   `ELR - ImageBase`.
3. In `DarwinBoot.c`, print a small stage token immediately before the
   request validation, ramdisk layout, kernel read/parse, ADT read/parse,
   video read, window allocation, image placement and kernel copy stages.
   The last token remains visible if the exception handler cannot expose a
   shared stage variable safely.
4. Keep the current countdown/manual menu behavior and do not retry
   automatically.

This diagnostic patch must be committed and pinned in the EDK2 and downstream
UniXNU source graphs before another candidate is built.
