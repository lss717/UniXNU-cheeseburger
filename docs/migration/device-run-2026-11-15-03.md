| Field | Value | Meaning |
| --- | --- | --- |

| IL | `1` | 32-bit instruction |
| WnR | `1` | Write or cache-maintenance operation |
| CM | `1` | Cache-maintenance fault |
| DFSC | `0x21` | Alignment fault |

## Exact symbolization

The runtime image base is `0x17ADBB000`; the ELR/LR pair uniquely agrees with
the linked map:

```text
ELR - base = 0x1378  InternalMemSetMem
LR  - base = 0x3AE4  Boot, return address after BL ZeroMem
```

The linked `Boot` code contains:

```text
3ad8: ldr x0, [sp, #0xe0]      ; allocated window
3adc: mov x1, x26              ; used = 0x3070000
3ae0: bl  0x2f50 <ZeroMem>

```

The faulting instruction at `0x1378` is:

```text
d50b7423    dc zva, x3
```

`ZeroMem` is therefore the operation that faulted, not the subsequent Mach-O
segment `CopyMem`.

## Root cause

`Platforms/Msm8998FamilyPkg/Drivers/msm8998Dxe/msm8998Dxe.c` maps:

```text
0xA1A10000 + 0x00200000
```

as `EFI_MEMORY_UC | EFI_MEMORY_XP`. This is the backing buffer used by
`InMemorySerialPortLib`.

At the same time, the 8 GiB platform RAM descriptor still described the whole
range starting at `0xA0000000` as `EfiConventionalMemory`. DarwinBoot therefore
received `AllocatePages(AllocateAddress, EfiLoaderCode, 128 MiB)` over that
range, including the uncached serial buffer.

`DC ZVA` on the device-mapped page at `0xA1A10000` raised the data-abort
alignment fault. The previous hypothesis that this was an ordinary
kernel-segment copy or a pool allocation above 4 GiB is not supported by this
run.

## Minimal fix

EDK2 commit:

```text
f3ca800eaf67a0450ee3445560da463cc0eab05c
fix(memory): reserve in-memory serial buffer
```

The 8 GiB RAM description is split into:

```text
0xA0000000 + 0x01A10000  EfiConventionalMemory
0xA1A10000 + 0x00200000  EfiReservedMemoryType / UNCACHED_UNBUFFERED_XN
0xA1C10000 + 0xDE3F0000  EfiConventionalMemory
```

This keeps the firmware's in-memory serial buffer working while preventing the
UEFI allocator from handing its pages to DarwinBoot.
