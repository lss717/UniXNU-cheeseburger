## Second final property return

The `_ml_parse_cpu_topology` second-final direct property return was tested with
a single-point PSCI reset:

```text
boot SHA-256    93cb960b8be09d557b4f39a11d80fffa2f757724727d65a0c0cfc9c065ed5cc2
kernel SHA-256  2447617f6e7912202c64f97ee75ff6567989e9f297cb9d10a1cf5b7cea265306
payload SHA-256 10b25d19b9e9b83f1f0d0e9222d5677e28127bfa6b5807fc741aa77d0ca4609c
VA              0xFFFFFFF0073F5830
file offset     0x3F1830
source word     0x7100041F
patch word      0x1418E2B0
```

After manual IOS selection, the device went black and did not restart. The
reset point was therefore not reached. This result proves that the stop is at
or before the second final `acc-impl-reg`/`cpm-impl-reg` direct property return.

```text

kernel SHA-256  cccbd654572a9cda2ddc71e2ec2407f23a3f513c462d83ab3aad163e94227dcb

VA              0xFFFFFFF0073F580C
file offset     0x3F180C
source word     0xF90016C8
patch word      0x1418E2B9
```

After manual IOS selection, the device again went black and did not restart.
The reset point was not reached, narrowing the stop to:

```text
0xFFFFFFF0073F5704 .. 0xFFFFFFF0073F580C
```

The candidate passed 47/47 ADT checks, FD/FV module checks, boot header and load
range checks, manifest validation, and a byte-for-byte comparison of the
payload-embedded kernel against the candidate kernel.

The first direct property call itself was tested:

```text
VA              0xFFFFFFF0073F57E4
file offset     0x3F17E4
source word     0x9415331E  BL

boot SHA-256    eb126091bef37e3f51299a1d55b93813ca8d5ae281e1a3c455a15fff454e4819
kernel SHA-256  27ce5260512bfdc2b4d4eb61e33560fa51580336d8d4a67d5d51b313c208f241
payload SHA-256 191ddd364089811a8cd841a7947a49b4eaed483c78f22a3017197496a5a01931
patch word      0x1418E2C3
```

- Immediate reset: execution reached the first direct property call.
- No reset: the stop is before that call, inside
  `0xFFFFFFF0073F5704 .. 0xFFFFFFF0073F57E4`.

The device went black and did not restart again. This proves that execution did
not reach the first direct property call, narrowing the stop to:

```text
0xFFFFFFF0073F5704 .. 0xFFFFFFF0073F57E4
```

The candidate passed the structural, ADT, manifest and embedded-kernel checks.

## Type-two branch boundary

Disassembly shows that the first branch after the known `0x5704` checkpoint is:

```text
0xFFFFFFF0073F5728  B.EQ 0xFFFFFFF0073F5920
0xFFFFFFF0073F572C  ADRP x8, ...
```

The next single point is the fall-through at `0x572C`:

```text
VA              0xFFFFFFF0073F572C
file offset     0x3F172C
source word     0xB0FFEC68  ADRP

boot SHA-256    a75721dbfa8a489c8d8425dda2590416720cc5f3b190b4d5d6cb3149838473a9

payload SHA-256 16a3151e4b385a6c647de87d3046619c53ea28adee9016172cae82bbc49c777b

```

- Immediate reset: the `w8 == 2` branch at `0x5728` was not taken.
- No reset: execution took that branch, or stopped before `0x572C`.

The candidate passed the same structural, ADT, manifest and embedded-kernel
checks and was staged at:

```text
E:\WindowsData\Project\ios-backups\op5-20261116-topology-type2-branch-probe
```

At validation time the device was black with no ADB or Fastboot enumeration, so
the candidate was not started automatically and no partition was written.
